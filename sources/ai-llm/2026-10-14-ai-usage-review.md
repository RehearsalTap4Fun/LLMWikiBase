# 2026-10-14 AI 使用经验回顾：可解释功能与端到端发布验证

## 覆盖范围

- **Cursor**：同一份带完整日期时间的 Agent transcript 记录了扑克项目的观察员评价设计与实现、部署到既有云端站点、以及一段未完成的移动端适配审计。
- **Claude Code**：两次 JSON-only 会话，分别提取历史材料中的待办和按 `build`、`cost`、`reach` 独立评分两个 App Store 应用。
- **Codex Desktop**：当天仅有上一轮经验沉淀自动化；其结论已在前一日记录，不重复作为本页核心证据。

## 关键经验

### 优先把现有分析能力包装成可解释功能

扑克“观察员”没有另接 LLM，而是设计成纯前端、确定性的规则引擎：复用已有胜率模拟、范围推断、基线策略和 ICM 计算，对每次行动给出评价。这样的边界适合离线单机游戏：延迟、成本和可复现性可控，评价也能回放。

实现时应在行动结算前抓取状态和展示范围，避免 `act` 之后范围突变造成错位；使用带手局种子的随机数，使胜率估计和评语变体可复现。评价只使用玩家手牌与公开可推断的范围，不能读取对手底牌或内部“上帝视角”范围；这既保持公平模式，也防止结果导向解释。

**可复用做法：**先列出产品中已有、可信的计算模块，再定义一层独立的 `context -> structured verdict` 适配器；将文本展示放在适配器之外。为回放保留可选的结构化评价记录，而非只存最终文案。

### 发布脚本应把验证和回滚写进流程

部署流程将测试、构建、上传和线上 HTTP 回读串成一个命令。首次接入 nginx 时，先备份配置，插入规则后执行 `nginx -t`，仅在通过时 reload，失败则恢复备份；随后检查新路径、入口页和既有三个站点的状态码，并在浏览器实际开始一局来验证 Web Worker 与观察员功能。

**可复用做法：**把“构建成功”与“生产可用”分开验证。脚本中至少包含构建、上传、目标 URL 健康检查；改反向代理时必须有配置测试和可执行回滚。最后用一次真实用户路径验证动态资源，不只检查首页 200。

### 界面自动化受阻时，以状态快照替代重复截图

移动端适配审计先用设备尺寸模拟和截图检查大厅、牌桌与行动区；截图缩放和行动区出现时机不确定后，尝试通过 DOM 几何数据核对布局。会话最终因重复恢复而停止，说明在“截图与状态不一致”时继续重试无法提高证据质量。

**可复用做法：**为 UI 检查设定有限重试次数。若视觉结果与预期状态矛盾，立即采集 viewport、关键元素 bounding box、可见性和交互状态；仍不能解释时，记录阻塞并换用真实设备或可控浏览器会话，而不是继续刷新/截图。

### 严格 JSON 输出适合后续机器处理，但不替代事实校验

Claude Code 的两次任务都通过“只输出 JSON 数组/对象、字段和评分锚点固定”的提示得到可机器消费的结构。三维评分中要求分别定义锚点、理由指出最致命短板，有助于避免把技术难度、成本和获客混成单一印象。

但可行性理由中的硬件依赖、授权和市场判断来自提示内有限信息，应作为待验证假设；结构化输出保障的是格式与决策框架，不是外部事实的真实性。

## 可复用检查清单

1. 新功能先复用已有的可解释计算，明确输入快照、可见信息边界和回放数据结构。
2. 对含随机模拟的评价固定种子或记录种子，保证同一局面可重现。
3. 发布自动化覆盖构建、上传、健康检查、代理配置测试、回滚和真实用户路径。
4. UI 自动化出现观测矛盾时改采状态快照，并设置重试上限。
5. 机器消费任务固定 JSON schema；涉及市场、政策或授权的断言另行回源核验。
