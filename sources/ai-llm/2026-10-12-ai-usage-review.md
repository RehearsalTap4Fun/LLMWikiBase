# 2026-10-12 AI 使用经验回顾：受限抽取与独立评估

## 覆盖范围

- **Claude Code**：一段会话从近期 Git 状态和会话消息中提取“尚未完成、值得今天跟进”的待办；另一段以固定 JSON schema 对 10 个 App Store 应用做独立开发可行性初筛。
- **Codex Desktop**：仅发现每日知识库沉淀自动化；它复核并推送了前一天的记录，没有新的独立工作内容。
- **Cursor**：当天有进程日志，但没有可读取且带当天时间戳的对话转录；不纳入结论。

## 有效做法

### 1. 用封闭证据池和严格输出契约做信息抽取

待办提示限定了输入来源、筛选条件、最大数量、字段长度、难度枚举和空结果 `[]`，并要求只输出 JSON。这样的约束把聊天式总结转成了可以直接进入后续脚本或看板的结构化数据。

可复用模板：明确证据池 → 定义入选和排除标准 → 指定 schema/枚举/数量上限 → 声明“证据不足则空数组”。

### 2. 评估矩阵要拆开维度，并保留决策短板

应用初筛把 `build`（技术复刻）、`cost`（边际成本）和 `reach`（获客与冷启动）分开评分；每档都给出锚点，并要求理由点出最致命短板和 MVP 工期。该结构适合后续按维度筛选，而不是把“容易开发”误当作“值得做”。

此类输出只是基于给定应用描述的假设性初筛。要做投入决策，仍须回查版权/IP、数据源条款、真实 API 定价、竞品获客成本和订阅转化等外部事实。

## 失败模式与修正

### 历史会话文本不等于当前未完成事项

待办提取结果把“配置每日定时拉取”和“切换 dataconfig 到 dev”列为待办；但同一输入中的历史会话已记录这些操作完成。这说明即使提示写了“不要把已完成的事列进来”，模型也可能因原始片段缺少明确状态边界而误把旧请求当成待办。

修正方式：在输入预处理时为每段材料附上时间和状态（`open`、`done`、`superseded`）；或在提示中规定“只有最后一条用户消息明确要求、且其后没有完成确认的事项才可输出”。对自动执行的待办，保留源会话 ID 与时间戳，并在落库前做状态回查。

## 可复用检查清单

1. 结构化抽取先收紧证据范围和状态，再要求机器可读的空结果与固定 schema。
2. 多维评估为每个维度给独立锚点；理由必须暴露最弱环节，而非只给总分。
3. 把模型的市场/成本判断视作候选假设，关键外部事实必须回源验证。
4. 待办自动化应去重并过滤已完成、被替代和过期的历史会话。
