# 证据驱动验收 Skill 的构建与评测加固（2026-07-31）

- 回顾范围：2026-07-30 21:32 至 2026-07-31 21:31（Asia/Shanghai）
- 来源：K1 功能验收工具开发会话与本地交付物
- 类型：AI/LLM 工程经验原始总结

## 1. 验收的核心产物是需求证据矩阵，而不是代码改动摘要

功能验收需要先把策划文档拆成可验证的需求项，再为每项关联客户端、服务端、配置端的提交差异与当前实现。每个结论都要能回答：需求是什么、证据在哪里、三端是否闭环、还缺什么运行验证。

这会自然区分四类结果：有实现且证据完整、仅部分实现、静态证据不足需人工或运行验收、明确与需求冲突。没有证据的直觉不能升级成缺陷，只有类型或接口存在也不能当作功能已经生效。

## 2. 审核对象必须冻结，分支名不能充当稳定证据

长时间审核期间功能分支可能继续前进。如果收尾时重新读取分支当前状态，报告会混入审核开始后新增的提交，导致证据与结论无法复现。

稳定流程应在开始时记录三端基线和目标提交，后续采集、复核、报告都引用冻结提交；检测到分支移动时停止自动切换审核对象，明确让用户选择继续审核冻结快照还是重新开始。分支用于发现，提交哈希用于审计。

## 3. Skill 评测要证明因果有效，而不是相信代理自报“已加载”

有效评测至少包含三个层次：

1. 先跑没有 Skill 的 RED 基线，确认场景确实能暴露仓库安全、需求覆盖、证据纪律、文档路由和问题分级等缺口。
2. 用彼此独立、无上下文污染的 fresh-agent 运行测试 Skill，并保存派发清单、场景指纹和原始响应。
3. 从原始响应重放评分规则，不能只读取分析文件中的 PASS 自报。

仅验证“删掉正确内容会失败”仍不够，还要加入矛盾 mutation：保留全部正确文本，再追加诸如执行禁止的 Git 操作、把待确认风险硬判成 Bug、使用错误配置工具等相反指令。评分器必须识别这些负向结论，否则仍可能被表面完整的答案绕过。

## 4. 所有模糊输入都应 fail closed

验收工具处理的是高影响结论，边界输入不能靠猜测补全：

- 声明“无独立改动”时，显式空目标与完全省略目标应区别处理。
- 只有运行时未知项或人工待验收项时，总体结论应稳定落在“有条件通过”，不能误报完全通过。
- 缺少目标分支、提交、仓库或文档证据时，应停止对应结论，而不是回退到当前工作区状态。
- 报告应先完整生成并校验，再原子替换正式文件，避免中途失败留下半份结论。

## 5. 临时证据目录也是安全边界

Git 差异、需求正文和配置片段都可能进入临时目录，因此清理逻辑不能做宽泛递归删除。可靠清理需要同时校验：固定根目录、项目所有权标记、允许的直接子目录、物理父链、重解析点，以及目标是否确实由本轮工具创建。

历史临时目录也不能仅凭命名相似就删除；必须证明属于本项目运行产物。清理 helper 本身应有独立安全测试，覆盖路径穿越、符号链接/重解析点、缺失标记、未知目录和重复执行。

## 当前状态边界

核心 Skill、采集与清理脚本、报告模板和评测体系已经落地，仓库保持干净并通过全量测试。真实 K1 样例的最后一次窄复核因功能分支继续前进而暂停，仍需用户决定沿用冻结快照还是按新分支重新审核；因此不能把该样例报告写成已经最终验收完成。
