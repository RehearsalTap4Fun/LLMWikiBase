# GitHub 增长简报自动化经验回顾（2026-07-31）

- 回顾范围：2026-07-30 21:32 至 2026-07-31 21:31（Asia/Shanghai）
- 来源：期间内活跃的 Codex 会话与自动化实跑结果
- 类型：AI/LLM 自动化经验原始总结

## 1. 公开事件流只能称为“观测新增”，不能冒充全站净增量

GitHub Archive 可以通过 `WatchEvent(action=started)` 和 `ForkEvent` 统计公开事件流中的新增 Star、Fork，但它不提供取消 Star 等反向事件，也不保证覆盖 GitHub 的全部真实变化。因此榜单标题和说明必须明确使用“事件口径的观测新增”，不能称为全站真实净增量。

判断数据是否可信不能只看小时文件是否齐全。即使完整处理了所有小时文件，也要同时检查事件总量、目标事件分布、解析错误和榜首增量是否合理；如果绝对值明显偏低，应把数据源覆盖限制写进简报，而不是把异常解释成市场趋势。

## 2. 时间窗口应锁定完整小时，并把缺失小时作为一等状态

稳定做法是以自动化运行时为基准，选择最近一段已经结束的完整 UTC 小时，再换算为北京时间展示。每个小时文件独立下载、校验和缓存，可避免网络中断后重做全部工作。

缺失小时的处理规则应预先固定：

- 对单个失败小时只做受控重试，不无限重试。
- 重试仍失败时，用其余完整小时继续生成榜单。
- 在标题下醒目标注“数据不完整”、缺失时段、实际覆盖范围和失败原因。
- 完全没有事件数据时输出失败简报，不用累计排名或 Trending 补位。

这种设计把“部分成功”变成可解释结果，而不是把数据缺口静默吞掉。

## 3. 排名、元数据补全和不可访问仓库要分层处理

Star 与 Fork 是不同信号，应分别排行，不能用未经说明的权重混成一个综合分数。稳定排序可以依次使用：观测新增量、当前对应总量、仓库全名。入榜候选再通过 GitHub API 补充当前总量、主语言、简介和链接。

元数据阶段仍可能遇到仓库删除、转为私有或临时不可访问。此时应跳过该仓库并从候选池继续补足榜单；同一仓库进入两榜可以保留两次，但要显式标注“双榜上榜”。

## 4. 外部消息发送必须与数据生成解耦，并保证至多一次

简报先在本地完整生成并通过检查，再进入发送阶段。发送前核对目标群、标题、日期、正文首行、无 @ 参数、无凭据和本机路径；Webhook 凭据仅在运行时读取，不能写入自动化配置、缓存或日志。

机器人返回值还要做语义归一化。本次实跑中，服务明确返回成功，但封装脚本曾把字符串形式的成功码误判为失败。正确做法是同时兼容数值和字符串成功码，并把“远端明确成功”作为最终发送状态；一旦远端成功，绝不能因本地退出码异常再次发送。

可复用原则：生成可重试，发送不可盲目重试；发送前固化消息，发送后只记录脱敏状态。
