# Codex 会话执行与人工门禁生成工作流（2026-08-12）

- 回顾范围：2026-08-11 21:30 至 2026-08-12 21:31（Asia/Shanghai）
- 来源：历史人物形象传记生成器设计与工程核心流程
- 类型：AI/LLM 使用经验原始总结

## 1. 单人原型可以把 Codex 会话作为生成执行层

当产品只服务单人内部使用、希望复用 Codex 订阅能力，又不需要无人值守队列时，可以让 Web 工作台只负责准备受控参数、展示结果与导出；真正的文本和图片生成由用户在当前 Codex 会话中显式触发。

这种架构避免了额外的模型服务、密钥管理和后台常驻进程，同时保留了可视化配置与审核体验。边界必须写清：它适合人工在环的本地原型，不适合公开、多用户或批量生产服务。

## 2. 生成前先冻结人物卡与请求契约

历史人物生成不应让模型自由补全事实、装备和姿态。人物卡应预先保存可引用事实、来源定位、可信类型、允许姿态、服饰与装备约束，以及禁止元素；请求只能从这些受控选项中选择。

开始生成前校验人物卡、请求和场景模板的版本化 Schema。短传中的每个事实性句子必须映射到已批准的事实和来源；图片提示词必须继承人物卡约束。Schema 或映射不完整时应拒绝执行，而不是边生成边猜测。

## 3. 技术审查不能替代人工批准

AI 可以核对人物卡的结构、来源完整性和内部一致性，但不能自行把人物卡标记为“人工批准”。当数据将成为后续生成的事实权威时，批准动作必须停在明确的人工边界，并记录审核人和不可变审批结果。

同理，图片和传记可以先进入 `needs_review`，保留最佳候选与问题清单；只有所有关键检查通过且用户明确确认后，才生成批准记录和可验证导出包。确认接口应由系统生成审核字段，拒绝客户端自填审核身份或结论。

## 4. 重做任务必须保留父子来源关系

图片重做、传记重做、完整重试和人工编辑复核不是同一种任务。每种任务都应明确允许生成还是继承图片、是否允许新增尝试、父任务需要达到什么状态，以及哪些成品必须原样继承。

可复用做法是建立 `task_type × provenance` 矩阵：

- 只重做传记或复核人工编辑时，图片必须从父任务继承，不能调用图片生成；
- 重做图片或完整重试时，才允许产生新的图片尝试；
- 子任务记录父任务标识，但不继承父任务的人工批准；
- 所有重做创建新任务目录，不覆盖父任务历史成品。

只相信子任务草稿自己声明的来源，会产生“声称继承、实际重生成”或“传记重做夹带新图片”的绕过路径。

## 5. 关键质检项由场景推导，不能由草稿降级

全身完整、脚部、服饰年代和禁止元素可以是所有图片的固定关键项；坐骑关系、兵器动作和甲胄则应根据当前姿态、场景必需物件和人物约束动态推导。

生成草稿只能提交检查结果，不能决定哪些检查是关键项。打包器应验证检查 ID 集合完整、唯一且与权威清单精确相等，再验证每一项的关键性与当前场景相符。仅比较列表长度会被“重复一个 ID、漏掉另一个 ID”绕过。

## 6. 本地文件工作流仍要防止竞态与替换

不可变任务应先取得同任务标识的独占预约，在临时目录写入并完成校验后再发布；失败方不得接触最终目录。读取父任务成品时，应拒绝符号链接和非普通文件，并在同一打开句柄上核对文件身份、大小和修改状态；通过校验的字节应直接用于发布，不能在校验后按路径重新打开。

这能减少检查与使用之间被替换的窗口。预约的清理也要验证目录归属和所有者令牌，不能因为超时就删除另一个仍在工作的进程状态。

## 7. 评审修复需要反例和新鲜上下文验证

这类生成系统的高风险点通常不在“正常路径是否能跑”，而在同步篡改、父子任务混用、空映射、重复清单、陈旧响应、并发确认和恶意文件结构。每个 finding 应先补能真实失败的反例，再实现修复并运行完整门禁。

独立评审者应读取冻结的变更对象，逐轮复核旧 finding 是否关闭并寻找新破坏；Skill 还应使用新鲜上下文跑用户式请求，验证它能自行恢复任务边界，而不是只在知道预期答案时通过。

可复用原则：人工在环不只是界面上的“确认按钮”，而是贯穿事实权威、任务来源、质检关键性、不可变发布和导出资格的一整套契约。
