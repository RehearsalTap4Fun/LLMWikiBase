# Codex 用量上报端点迁移的最小变更与真实事件验收（2026-08-19）

- 回顾范围：2026-08-18 21:31 至 2026-08-19 21:31（Asia/Shanghai）
- 来源：Codex 用量上报从团队版切换到个人版的修改与重启验证会话
- 类型：AI/LLM 经验原始总结

## 1. 先列出所有上报入口，再做最小替换

一次版本端点迁移可能同时涉及日志、指标、链路追踪和事件上传脚本。只改其中一个入口会形成“部分数据进入新版本、部分仍留在旧版本”的隐性分流。

迁移前应列出所有端点、上传脚本基地址、身份标识和触发配置，明确哪些字段需要变化、哪些必须保持不变。本次保留原有用户归属与 hooks 触发方式，只切换版本路径，降低了无关回归风险。

## 2. 验证必须同时包含正向与反向断言

只检查新地址存在不够，还要确认旧地址完全消失。建议至少验证：

- 所有遥测端点都指向新版本；
- 上传脚本使用同一版本基地址；
- 用户归属标识没有意外变化；
- hooks 配置哈希保持不变；
- 配置文件与脚本语法能够正常加载；
- 全局搜索不再发现旧版本地址。

先备份，再做窄范围字符串替换，并比较备份与新文件的差异，可以证明修改没有扩散到其他设置。

## 3. 配置检查通过不等于运行时已经生效

桌面应用只有重启后才会让新进程继承更新后的配置和环境。最终验收应发送一次真实用户消息，并检查用户提交和会话结束两类事件是否都命中新端点、收到成功响应。

日志审查要把一次事件的发起行与成功行配对，不能仅看到“开始上传”就判定成功。本轮重启后的连续事件均形成了发起与成功闭环，证明切换已经进入实际运行路径。

## 4. 凭据与端点信息不应进入总结产物

排查脚本可以读取运行时配置，但输出和知识沉淀只记录布尔结论、事件类型与响应状态，不打印令牌或完整敏感地址。这样既保留验收证据，也避免把凭据复制到会话、报告或知识库。
