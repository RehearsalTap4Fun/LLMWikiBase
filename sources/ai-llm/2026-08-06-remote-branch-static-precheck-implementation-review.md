# 远端分支静态预检落地经验（2026-08-06）

## 背景

远端分支审核的难点不在于“读取另一个分支”，而在于同时保证审核对象可复现、本地开发现场不受影响，并且远端读取失败时不悄悄换成旧数据。本次在既有设计基础上完成实现、全量验证和真实远端冒烟，形成了以下可复用经验。

## 先冻结审核对象，再收集证据

- 用户给出的是会移动的远端引用，报告真正审核的对象应是解析后冻结的提交标识。
- 引用解析完成后，配置、代码、测试用例和报告都必须围绕同一个冻结对象读取，不能在流程中再次解析远端引用。
- 报告应同时记录来源、远端引用和冻结对象，让审核结果可以回溯到确切输入。

## 用隔离对象缓存代替切换正式仓库

- 正式客户端、服务端和配置仓库只作为远端来源信息，不在其中切分支、创建工作树或改写索引。
- 独立对象缓存只保存审核所需对象，避免为了静态检查复制完整仓库。
- 普通文本可直接从对象数据库读取；大文件仅在确实需要内容时，才在隔离缓存中精确物化目标对象。
- 缓存键必须绑定远端来源与冻结对象，防止不同远端或不同提交之间复用错误证据。

## 失败时宁可停止，也不要隐式降级

- 远端不可达、引用不存在或对象不完整时，应明确失败。
- 不应自动改用本地同名分支或过期的远端跟踪引用，因为这种降级会让报告看似成功，实际审核了错误版本。
- 缓存命中也必须先验证对象身份和完整性，不能只按目录存在判断可用。

## 验证要覆盖结果与副作用

- 功能验证不仅要检查报告是否生成，还要覆盖远端解析、缓存复用、按需大文件读取和失败路径。
- 真实远端冒烟应分别记录首次准备与缓存复用后的耗时，避免把冷启动成本和日常增量成本混为一谈。
- 运行前后都要采集正式仓库的当前分支、提交位置和工作区摘要；只有三者保持一致，才能证明预检没有打断本地开发。
- 报告中的测试用例证据链应与冻结对象一起发布，避免“代码来自目标版本、测试依据来自当前工作区”的混源问题。

## 完成边界

“设计完成”“实现完成”和“真实远端验证完成”是三个不同状态。只有实现通过自动化验证、真实远端冒烟和正式仓库零变化检查后，才能把该能力描述为已经落地。
