## 1. Jenkins Token 认证需要用户名配合

Jenkins 的脚本访问通常使用用户名与 API Token 组成的 Basic Auth，而不是只传 Token 或使用 Bearer 头。接入时应先用只读接口验证鉴权和权限范围，再读取具体任务的参数定义。

凭据配置应满足：

- 配置文件不进入版本控制。
- 输出和日志不打印用户名、Token 或认证头。
- 文件权限尽量限制为当前用户可读。
- 只在运行时读取凭据，不复制到日报、经验文件或自动化记忆。

## 2. 任务参数应形成场景模板

本地服务器部署、服务器数据重置和热更属于不同风险级别的任务，不能共用一套默认参数。

- 部署场景：用户提供分支和服务器，自动映射到代码、配置与目标服务器参数；提交前检查是否已有同服重复构建。
- 数据重置：属于破坏性操作，即使有默认范围，也必须在执行前复述服务器和清理范围并取得明确确认。
- 热更：先读取参数和版本预览，不因用户只发任务链接就自动触发。

自动化日报应把“任务已启动”与“部署完成”分开。本次只确认部署进入构建流程，没有证据时不能写成部署成功。

## 3. Windows 下 Git 无法替换工作簿通常是文件句柄问题

当 Git 恢复工作簿时报无法删除旧文件，先检查文件是否只读、Git 索引状态和进程占用。若文件不是只读且索引正常，而 Windows 拒绝独占打开，通常意味着 Excel、WPS、预览工具或后台脚本仍持有文件句柄。

本次定位到后台 Python 任务占用目标工作簿，说明 Codex 或数据处理脚本也可能成为锁源，不能只排查 Excel。

## 4. 解除占用与丢弃修改是两个独立决策

停止占用进程只会释放文件句柄；随后执行 Git 恢复会丢弃本地修改。安全处理顺序应为：

1. 确认占用进程对应的任务是否仍需保留。
2. 结束或正常关闭该任务。
3. 重新检查文件已无占用。
4. 明确确认允许丢弃本地改动后，再执行恢复操作。

不能因为用户贴出了 Git 错误，就默认有权限终止任务或覆盖工作簿。

## 5. 自动化状态表述要精确

- 鉴权成功：只表示具备相应权限，不等于任意任务都可执行。
- 进入队列：不等于获得构建号。
- 构建已启动：不等于构建成功。
- 参数已读取：不等于任务已触发。

把这些状态分开记录，可以避免日报和后续自动化夸大执行结果。
