# 静态验收中的测试用例证据链经验（2026-08-03）

- 回顾范围：2026-08-02 21:31 至 2026-08-03 21:30（Asia/Shanghai）
- 来源：K1 功能验收 Skill 改造与新服大地图重构实跑会话
- 类型：AI/LLM 工程经验原始总结

## 1. 测试用例是需求的验收投影，不是新的需求权威

把测试用例接入静态验收能显著提高需求拆解的稳定性，但用例不能覆盖开发文档，也不应与开发文档冲突。无论用例由测试人员提供还是由 Skill 自动生成，主开发文档仍决定业务范围和优先级。

可靠的证据顺序是：先从开发文档建立稳定需求树，再把每条用例映射到需求与可验证条件。如果人工用例与开发文档冲突，应报告冲突并暂停相关结论；如果自动生成用例出现冲突，则说明生成逻辑或需求解析有误，不能反过来修改需求含义。

## 2. 静态用例与运行用例应分层交付

本次流程为每条需求生成一条静态验收用例，同时为必须进入游戏才能确认的场景生成独立运行用例。两类用例承担不同职责：

- 静态用例要求定位文档、提交差异和最终实现证据，用于判断已实现、部分实现、未实现或无法确认。
- 运行用例描述环境、前置条件、操作、期望与需要保存的证据；在没有实际执行时统一保持“未知/未运行”。

运行用例未执行本身不能制造缺陷，也不能被写成已经通过。总体结论只能由确定性的静态问题和已经完成的验收结果驱动；未运行项继续作为后续动态验收清单。

## 3. 配置终态应以目标提交中的正式工作簿为准

大地图文档引用的《配置表结构》可能已经过时，只适合帮助定位候选表和字段；真正的配置最终状态是配置仓库目标提交中的正式 `.xlsx`。当结构文档与正式表冲突时，应以正式表和程序实际读取契约为证据，同时记录文档过时风险。

这次核查据此纠正了一个重要边界：不能用旧结构文档推翻正式表已经闭环的地图、拓扑、迷雾、颜色和对象关系，也不能因为结构文档声称某项取消，就忽略正式线上配置仍在投放相应目标。

## 4. Git LFS 配置必须按对象身份取证

从 Git 提交直接导出工作簿时，得到的可能只是 LFS 指针而不是 Excel 实体。稳妥做法是：

1. 从冻结提交读取 LFS 指针与对象标识。
2. 只使用与该标识校验一致的本地 LFS 对象。
3. 将实体复制到受控临时目录只读解析。
4. 核验完成后由项目清理器移除临时副本。

不能退回读取当前配置工作区，因为工作区可能已经切换到其他分支或含有未提交改动；那会把与审核目标无关的状态混入证据。

## 5. 实跑验证了“配置投放—程序语义—业务结果”的闭环检查

正式配置仍投放了一个依赖旧中心堡垒的联盟目标，但新地图规则已经取消该建筑，服务端也没有为该目标提供新地图替代语义。三类证据共同说明该目标在新服无法完成，可能阻塞对应章节和奖励；此外，部分界面与正式任务文案仍残留旧地图术语。

这类问题无法只靠代码 Diff 或配置搜索发现。必须同时回答：配置是否实际投放、服务端如何消费、玩家是否存在完成路径。测试用例把三段证据固定在同一需求下，使结论更容易复核。

## 6. 报告包要同时服务审计与后续测试

本次交付将静态验收报告与测试用例文档放在同一报告包中，并对需求覆盖、状态、问题引用、文件哈希和临时证据清理做发布后校验。报告负责说明为什么得出结论，用例负责说明未知项下一步如何验证。
