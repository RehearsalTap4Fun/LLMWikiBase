# PowerShell 解析 JSON 时间戳时要保留 DateTime Kind（2026-08-31）

## 背景

自动化按 UTC 时间戳筛选会话时，`ConvertFrom-Json` 会把带 `Z` 的 ISO 8601 字符串自动转换为 `System.DateTime`，并保留 `Kind=Utc`。如果随后把这个日期对象传给 `DateTimeOffset.Parse`，PowerShell 会先把对象转成不带时区的字符串，再按本地时区解释，导致时间整体偏移。文件名与解析结果相差固定时区，正是这种二次解析错误的信号。

## 可沉淀经验

### 1. 不要把已经解析的日期对象再次按字符串解析

当值已经是 `DateTime` 时，应直接强制转换为 `DateTimeOffset`，让运行时依据 `Kind` 保留 UTC 语义；或者在 JSON 转换前直接从原始文本提取时间字符串，再一次性解析。两种方案都应立即规范化为 UTC 后再与游标比较。

### 2. 调试时同时打印四种视图

至少比较原始 JSON 字符串、转换后对象类型、`DateTime.Kind`、直接转换结果和二次解析结果。若原始值带 `Z`，但二次解析结果出现本地偏移，说明时区标记在对象转字符串阶段丢失，而不是源数据本身错误。

### 3. 边界测试必须覆盖精确游标

测试应包含游标前、与游标相等、游标后以及跨午夜的样本，并明确使用左开右闭区间。还要覆盖带七位小数秒的 .NET 时间输出；不同语言的解析器不应只接受六位小数而拒绝合法的 ISO 8601 精度。

### 4. 自动化记忆保存的是时间点，不是显示文本

游标落盘时可以附带本地时区便于阅读，但下一次比较必须先恢复为明确偏移的时间点。禁止把无时区字符串当作 UTC 或本地时间猜测，否则连续运行会产生遗漏或重复统计。

## 适用场景

适用于 PowerShell 日志扫描、JSONL 会话回顾、增量同步、定时任务游标和跨语言运行元数据。核心原则是：保留原始时区语义，只解析一次，并用边界样本证明比较正确。
