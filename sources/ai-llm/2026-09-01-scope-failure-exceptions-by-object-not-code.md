# 失败例外应绑定具体对象，不能只按通用错误码放行（2026-09-01）

## 背景

渲染预检需要允许一个特定的可见口腔部件在资源加载失败时继续产出可度量结果。最初修复只按通用“资源加载失败”错误码放行，意外使眼睛、嘴型、头部附饰和特效等其他资源失败也绕过了原有阻断，扩大了失败语义。

## 可沉淀经验

### 1. 通用错误码通常不足以表达例外边界

同一错误码可能来自多个节点、槽位和业务阶段。若需求只允许一个特定对象例外，判断条件至少要绑定对象身份、当前选择和业务状态，不能把共享错误码当成授权范围。

### 2. 更稳妥的方式是建立精确容忍集合

先在发现阶段识别满足全部条件的具体诊断对象，再把这些对象加入容忍集合；后续预检仍对其他同码错误保持阻断。这样例外不会随着新增节点或复用错误码而自动扩散。

### 3. 正例和反例必须成对测试

正例证明目标对象的失败可以继续；反例要选择另一个使用相同错误码的对象，证明它仍然失败关闭。只测试“允许的例外成功”无法发现通用错误码造成的越权放行。

### 4. 修复报告要说明未改变的旧语义

除了描述新增能力，还应明确列出仍保持阻断的相邻失败类型。这样审查重点从“新路径是否能走通”扩展到“旧保护是否被意外拆掉”。

## 适用场景

适用于预检、权限、重试、降级、风控和任何需要为局部失败开例外的系统。核心原则是：例外授权给具体对象和条件，不授权给一个被广泛复用的错误标签。
