## 关键经验

### 1. 拆分“过载 ID”时，先按语义职责盘点，再改字段

`D2NpcTroopClassCfg.ID` 同时承担了三类职责：

- NPC 的业务身份与特殊类型判断；
- 运行时和协议中的展示/传递标识；
- `NpcTroopPowerCfg.Type` 的战力关联键。

因此新增 `Type` 不能做全局文本替换。更稳的做法是把每个引用点先归入“业务身份”“运行时拷贝”“协议语义”“战力关联”四类，再决定改为 `Type` 还是保留 `ID`。

这次审查还暴露出四个容易遗漏的跨层问题：

1. 客户端生成类已有同名 `Type` 属性，新字段会直接形成编译冲突；
2. 服务端路径清单少写一级 `game/`，说明清单行号正确也不等于路径可执行；
3. 旧客户端、服务端和 BI 若不能原子上线，既有协议字段静默换语义会造成灰度期错读；
4. 配置完整性既要正向检查“每个 NPC 都有战力组”，也要反向检查“每个战力组都有 NPC 定义”。

可复用结论：

> 配置字段改造的基本单位不是“字段名”，而是“字段在各消费端承担的语义职责”。

### 2. 分版本配置先确认是覆盖还是回退，再判断“总表有值为什么仍报错”

龙巢 NPC `13350001` 的空指针问题中，无后缀总表已有该行，但运行环境读取的是 `_10` 版本表。该版本表是完整替换，不会在缺行时回退总表，所以“总表存在”不能证明线上读取成功。

补齐主表后还必须继续沿消费链检查二级配置：

```text
D2NpcTroopClassCfg.ID
        ↓
NpcTroopPowerCfg.Type
        ↓
按 NPC ID + Level 创建战斗行为
```

只补第一个缺口，会把错误从“创建 NPC 时 nil”推迟到“创建战斗行为时缺战力配置”。

可复用排查顺序：

1. 确认实际加载的数据集、版本号和覆盖/回退规则；
2. 对比总表与版本表的行数及新增 ID 集合；
3. 沿运行时调用继续查所有二级索引和外键；
4. 数据补齐之外，在关键解引用处增加防御和可定位错误日志。

### 3. 工具输出只是“视图”，出现反常结果时要回到底层事实源

`MarchType.xlsx` 曾被读取工具显示为表头出现大量 `13`。直接检查 xlsx 内部 OOXML 后确认：真实单元格为空，是工具把带样式的空白单元格误解析成数值。

同类情况也出现在配置查询 CLI 暂不可用时：改用仓库中的 JSON 导出产物交叉验证，而不是猜测配置内容。

可复用证据优先级：

```text
原始 OOXML / 仓库文件 / 运行时代码
        > 可复现的导出 JSON/TSV
        > 表格预览或二次解析工具输出
```

当读数结果违反常识、与 git diff 不一致或大量重复时，应先验证读取链路，避免“修复一个并不存在的表格问题”。

### 4. 设计文档审查要把“规则正确”落成并发、迁移和验收约束

`NPC首杀规则.md` 的多角色审查发现，文档表面规则完整，但仍有两个 blocking 问题：

- 并发/重复结算只写“不得重复发奖”，没有唯一约束、事务或幂等键等实现保证，也没有可判定的验收观察点；
- `FirstKillOrderRequired` 可逐等级独立配置，但“顺序区间”被默认当作连续区间，未定义不连续配置是否合法。

其他高风险缺口包括：集结资格与“非目标”自相矛盾、历史迁移公式缺失、整体回滚未定义、加入集结是否服务端权威校验不明确、配置开关完整循环及 off-by-one 边界未覆盖。

另一个文档层经验是：玩法规则应使用玩家可理解的领域语言，不应把 `KilledLevels`、`ConsecutiveLevel` 之类程序字段写成规则定义；配置字段可以保留，但运行时存储结构属于实现设计。

可复用审查提问：

- 同一请求重放、并发到达时，唯一结果由什么保证？
- 配置允许表达的所有状态，规则都能唯一解释吗？
- 历史数据如何迁移、失败如何回滚、灰度期如何兼容？
- 每条“不得/必须”能否对应具体输入、操作、观察字段和期望值？

### 5. 线上异常定位要区分“玩家看到的结果”和“系统实际提交的状态”

世界杯切片异常里，玩家画面表现为三场全胜，但服务端收到的结算请求已经是 `2/3` 成功、平局。服务端只校验成功数与胜平负阈值是否一致，并不会根据画面或回放重算每个切片。

这把排查方向从“服务端把 3 胜算成 2 胜”收敛到客户端本地结果写入/覆盖和 UI 展示不一致。

可复用证据链：

```text
用户截图/操作时间
  → 客户端逐步骤事件与本地缓存
  → 最终请求 payload
  → 服务端校验与落库
  → BI/日志可观察结果
```

每一层都要明确“事实”“推断”和“当前不可观测项”。如果某类步骤按设计不上传回放，就不能凭缺失记录断言它成功或失败。

### 6. 数据分析经验文档必须区分通用流程、项目约定和单次案例

datain/BI 指南审查中，最主要的问题不是命令不够多，而是适用边界不清：通用 datain 流程与 K1/1047、世界杯活动专属表和口径混在一起，macOS 命令也没有声明平台范围。

一份可复用的数据分析指南至少应补齐：

- Skill 来源、版本或更新时间及最小可用性检查；
- 数据源、game code、表与字段的项目适用范围；
- 指标分子/分母、去重键、时间窗、时区、边界包含和空值规则；
- 权限不足、RAG 无结果、SQL 被拦、空结果、数据未更新时的停止/降级分支；
- 查询行数、CSV、正文数字、离线 HTML 与截图完整性的验收标准；
- 一次脱敏的端到端成功样例和最近验证日期。

核心原则：

> “有一套命令”不等于“别人能复现同一结果”；可复用经验必须同时记录上下文、失败行为与完成判据。

### 7. 项目专用 Skill 必须显式注册并持久化路由规则

一次 K1 配置任务误路由到 `xcfg-tool`，原因是：本地虽然存在 K1 的 `config-table-editor` 文件，但它没有出现在会话可用 Skill 清单中。对 Agent 来说，“磁盘上有文件”不等于“当前能力已注册”。

稳定做法应分两层：

- 在项目 `AGENTS.md` 持久化仓库路径和工具边界，例如 K1 正式配置、K1 测试配置、X1/X15 配置分别使用什么 Skill；
- 在 Skill 注册层让正确 Skill 可发现，同时在相似 Skill 描述里明确排除范围。

这比依赖某次会话口头纠正更可靠，也能避免错误工具对不兼容格式执行写操作。

### 8. UI 原型必须显式区分“评审 demo”和“工程交付”

怪物/泰坦首杀 UI 原型完成了素材复用、1×/2×截图读回和视觉 lint，但仍有首杀领取态、等级上下限、当前等级联动、专用滑条素材等动态缺口，且没有 tracked 工程改动。

所以正确交付表述应是“可评审候选”，而不是“功能完成”。视觉任务建议固定输出三张表：

- 已复用素材及缩放参数；
- 缺素材/占位表现；
- 动态状态、数据绑定与交互验收项。

### 9. 会话复盘必须先去重、再脱敏

本轮同时存在主会话、Claude 子代理、Codex 自动化和同一任务的复查会话。如果按文件数统计，会把一次审查重复计入多次经验。

此外，会话中出现过 MCP 访问密钥和设备标识。自动化复盘应只保留安全结论，例如“凭证明文进入会话后应轮换”，不得把原值复制到知识库或日报。

## 暴露出的失败模式

### 1. 只搜索直接 `cfg.ID` 会漏掉运行时复制和协议链

字段先被复制到 `CfgID`/`npcTroopID` 后，后续业务代码不再出现原配置名。只 grep 直接引用会得到一个看似完整、实际缺口很大的清单。

### 2. 修第一个 nil 不继续追二级配置，会把事故延后而不是消除

主配置补齐后，战力、奖励、行为或展示配置仍可能缺失。应以“对象完成一次核心生命周期”为终点追链，而不是以第一个报错消失为终点。

### 3. 评审清单有准确行号，不代表它已经可执行

路径前缀、命名冲突、发布顺序和验收缺口都可能让一份“引用准确”的清单仍无法安全实施。

### 4. 需要登录的页面访问失败后，不能把 URL 标题或用户描述当作正文

Claude onboarding 页面返回 403。正确结果是明确不可访问并请求用户提供内容，而不是根据链接猜测其中的经验。
