# README 作为可验证项目入口的维护经验（2026-08-07）

## 核心结论

README 不是项目历史的摘要，也不是能力愿景清单，而是新使用者进入项目时的事实入口。全面刷新 README 时，应从当前目录、规则文件、脚本和真实产物反向核对内容，让每一条能力描述都能落到可访问的事实依据。

## 推荐信息顺序

1. 项目解决什么问题，以及不负责什么；
2. 最短可执行的快速开始；
3. 输入、主产物与派生产物边界；
4. 从素材到澄清、生成、审核和同步的完整工作流；
5. 常用规则、模板和辅助脚本导航；
6. 典型示例与常见限制；
7. 依赖、验证方式和维护约定。

先让读者完成一次最小任务，再提供规则索引，比一开始罗列所有内部模块更容易使用。

## 能力描述必须回源

- 目录或脚本不存在时，不应继续保留旧入口。
- 已从骨架演进为可运行能力的模块，应改写为当前流程和真实产物。
- 动态工作区、精简审查和派生文档事实依据等新增规则，应链接到唯一权威说明。
- 规划文档是否归档、哪些目录是运行时生成，都应以当前仓库状态为准，不能沿用旧描述。
- 示例要指向仍存在、仍符合现行规则的产物。

## 验证分层

README 修改完成后可以独立验证：

- 严格文本编码与异常字符；
- 目标章节是否齐全；
- 所有相对链接是否存在；
- 命令、目录和文件名是否与仓库一致；
- 工作区是否只包含预期修改。

完整测试若在时间预算内没有返回结果，只能记录为“结果未知”或“超时”，不能因为文档检查通过而宣称测试通过。文档完整性验证和项目功能测试应分别报告。

## 删除过时内容的判断

过时描述通常包括：已经完成的骨架状态、早已变化的目录约定、只存在于旧计划中的工作流，以及与现行规则冲突的入口。删除前先确认是否仍有兼容或迁移价值；若没有，就直接描述当前状态，不在 README 中保留演进过程。
