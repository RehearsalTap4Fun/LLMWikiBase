# GitHub 增长榜基线隔离与补跑经验（2026-08-04）

- 回顾范围：2026-08-03 21:30 至 2026-08-04 21:31（Asia/Shanghai）
- 来源：GitHub 候选池增长榜自动化故障诊断、修复与补发会话
- 类型：AI/LLM 自动化经验原始总结

## 1. 手动补跑与定时任务不能共享“推进基线”的副作用

本次榜单没有内容并非采集失败，而是前一天的手动执行覆盖了定时基线，导致下一次日程只能得到过短的比较窗口。根因是“选择比较基线”和“推进下一次定时基线”被绑定在同一个状态写入分支中。

稳妥设计应把两件事拆开：定时运行成功后可以推进日程基线；诊断、回放和补跑可以显式选择比较快照，但默认不得改写定时基线。运行入口必须携带执行意图，不能仅靠是否传入某个通用参数猜测。

## 2. 补救运行要同时修复今天和保护明天

恢复当天榜单时，流程使用一份合格历史快照作为显式比较基线，重新采集当前候选池并生成正式榜单；与此同时保留当天定时快照，不让补跑再次污染次日窗口。

这类修复不能只验证“今天成功出榜”。还要在测试中确认：补跑前后的定时基线指针不变、下一次日程仍能找到正确前序快照、重复补跑不会改变比较语义。否则一次人工救火可能继续制造下一天的空榜。

## 3. 非榜单状态是正确结果，不应被空内容误导

当相邻快照间隔不满足最低要求时，即使候选池覆盖完整、采集没有失败，也只能输出“对齐基线”状态，不能估算增长或退回累计热度榜。这个失败关闭规则本身是正确的；问题在于状态简报没有让使用者快速看懂为什么没有排名。

状态消息应明确区分：采集失败、覆盖不足、快照窗口不合格和首次基线。对每种状态都给出原因、可恢复条件和下一次正常运行预期，避免用户把“无榜单”误认为“没有数据”。

## 4. 榜单生成与推送前要做结构化一致性审计

正式补发前，应逐条核对结构化结果与 Markdown 中的仓库、增长量和当前总量，检查标题日期、中文简介、正文关键词、无 @、无本机路径和无凭据。消息内容通过后再进入唯一一次真实发送。

发送成功后不再尝试修饰或重发同一榜单。数据采集与报告生成可以在发送前反复验证，外部推送则必须保持至多一次；幂等记录和脱敏回执只用于证明状态，不能持久化 Webhook 凭据。

## 5. 可复用原则

任何基于相邻快照差值的自动化，都应明确区分三种状态：候选数据、比较基线和下一次日程基线。手动操作可以选择前两者，但只有正式日程的受控成功路径能够推进第三者。把这一边界写进状态机和行为测试，比在事故后依靠操作约定更可靠。
