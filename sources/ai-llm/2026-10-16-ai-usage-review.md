# 2026-10-16 AI 使用经验回顾：把外部依赖说明做成可维护的产品路径

## 覆盖范围

- **Cursor**：Trip 项目为高德、Claude、DeepSeek、智谱等外部密钥补充申请指引。会话从代码中确认实际依赖和既有空状态，再核实申请 URL；随后集中配置链接、改造设置页和功能页提示，并执行类型检查、324 个测试与浏览器验证。
- **Claude Code**：一段定时待办抽取把混合历史会话压缩为受限 JSON；另一段以 `build`、`cost`、`reach` 三个独立维度评估单个 App 的可行性。
- **Codex Desktop**：当天可读记录只有前一轮经验沉淀自动化，未发现额外可独立提炼的会话。

## 关键经验

### 将外部依赖信息集中维护，再按界面承载能力分层呈现

密钥说明原先散落在设置页和多个功能空状态中，且各处覆盖不一致。有效改法是用一个共享模块维护“提供方—申请页—文案”，设置页作为完整入口展示可点击链接，能够渲染 JSX 的功能面板直接附对应申请链接；toast、按钮标题、错误字符串等纯文本位置只引导用户前往设置页。

**可复用做法：**先盘点真实依赖、设置入口与全部“缺配置”路径；将 URL 和展示名作为单一事实源，避免页面之间漂移。不要把不能点击的错误文案硬改造成不可靠链接，而是确保它有清晰的可达入口。第三方地址在写入前应实际核验，且把自建中转口令与可向平台申请的 API Key 区分开。

### 对用户可见配置改动使用“静态 + 运行时”双重验证

本次先通过类型检查和 324 个测试确认不破坏既有逻辑，再启动临时开发服务器，用浏览器检查设置面板、模型切换后的文案和缺 Key 卡片。验证后关闭自己启动的临时服务，并明确没有影响另一个项目已在运行的服务。

**可复用做法：**配置/文案任务也要先跑项目的自动化检查；只要涉及链接、条件文案或布局，就补一条真实空状态的视觉验证。启动本地服务时记录端口和归属，收尾仅关闭本任务启动的进程。

### 强约束输出与独立量尺提升自动化结果的可用性，但不替代状态判断

待办抽取使用严格 JSON schema、有限枚举和数量上限，产品评估则把技术复刻、边际成本、获客难度拆成互不影响的评分轴，并要求解释点出最致命短板。这使输出可被下游消费，也防止“容易开发”被误当成“值得做”。不过待办抽取仍会把历史请求误识为未完成事项，必须结合最后状态或提交证据过滤。

**可复用做法：**为机器消费结果明确字段、类型、枚举、上限和“宁缺毋滥”策略；为多维评估提供相互独立的锚点。任何“尚未完成”的判断都要以最后可见状态为证据，不能只读任务最初的请求。

## 行动清单

1. 为有外部 Key、令牌或账号前置条件的功能维护一张“依赖—获取方式—设置入口—降级行为”清单，并让 UI 文案从共享配置读取。
2. 把空状态浏览器验证列入涉及条件文案、链接或设置面板的最小验收项。
3. 定时待办抽取在输入中保留每个候选任务的最后状态、提交或验收证据；证据缺失时默认排除。
4. 独立开发评估继续使用互相独立的 `build` / `cost` / `reach` 量尺，并将外部事实核验与模型评分分开保存。
