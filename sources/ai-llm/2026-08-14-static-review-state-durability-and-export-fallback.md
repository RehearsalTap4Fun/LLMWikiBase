# 静态审核页面的状态持久化与导出兜底（2026-08-14）

- 回顾范围：2026-08-13 21:32 至 2026-08-14 21:31（Asia/Shanghai）
- 来源：历史人物批量生图审核流程的保存故障、状态恢复与目录收口
- 类型：AI/LLM 使用经验原始总结

## 1. 浏览器内存不是审核结果的最终载体

静态审核页可以承担低成本的人机协作，但审核状态如果只存在于当前标签页，一次刷新、关闭或浏览器崩溃就可能让整批人工判断丢失。页面内状态适合交互，项目内的单一审核结果文件才适合跨会话继续执行。

更稳妥的分层是：

- 用户每次操作后立即写入浏览器本地暂存，防止意外刷新；
- 明确保存时生成完整、可独立解析的审核结果；
- 下一轮自动化只读取已落盘结果，不从聊天描述猜测审核状态；
- 展示型占位条目与需要审核的正式成果分开，避免把占位内容误写进审核文件。

## 2. 保存必须是一条有反馈的降级链

本地静态页对文件选择器和直接覆盖文件的支持会受浏览器、安全上下文和权限影响。只提供一个“保存”按钮，并在异常时静默停止，会让用户误以为操作成功或页面无响应。

建议把保存设计成逐级降级：

1. 已获得文件句柄时直接覆盖目标文件；
2. 不支持或调用失败时下载完整结果文件；
3. 下载仍不方便时允许复制完整结果文本；
4. 每条路径都显示明确的成功、失败或下一步提示。

输入校验失败也不能只在页面顶部显示一条笼统提示。应定位到具体人物或卡片，并尽量把备注设为可选；真正必填的内容要在用户点击保存前就显式标记。

## 3. 外部浏览器状态通常无法由代理直接接管

即使浏览器扩展已连接，代理也未必能读取普通 Chrome 中 `file://` 页面已经存在的 JavaScript 内存。截图可以恢复少量可见信息，却不适合作为整批结构化审核结果的常规通道。

因此，流程设计不能依赖“出问题时让代理进入当前标签页取状态”。更可靠的边界是让页面主动导出文件或文本，再由代理读取本地成果。浏览器连接应当是便利能力，而不是数据持久化机制。

## 4. 简化目录时必须检查用户实际看到的根目录

在 Git 工作树中完成结构扁平化，不代表项目根目录已经变简单。如果成果仍停留在隐藏工作树，而根目录保留旧应用、缓存和历史产物，用户看到的仍是两套并存的项目。

收口前应同时核对：当前分支、用户实际打开的目录、隐藏工作树、未跟踪文件和最终保留清单。迁移后再检查旧路径引用、成果包完整性和工作区状态，并确保删除内容可以从版本历史恢复。

## 5. 最小可恢复审核包

适合个人批量生成项目的最小闭环可以是：

- 一个静态总览页；
- 每个正式对象一份图片、说明、提示词和结构化资料；
- 一份审核结果文件；
- 少量生成规则；
- 一张可复用的展示占位图（如有需要）。

关键不是文件少，而是每类信息只有一个权威位置，并且人工判断能够可靠跨越浏览器、会话和设备边界。
