# 富结构文档同步需要结构级往返验收（2026-08-25）

## 背景

把本地 Markdown 同步到在线协作文档时，接口返回成功、标题数量正确、表格块数量没有变化，都不足以证明内容完整。在线编辑器会把某些 Markdown 字符重新解释为待办、段落或转义文本；读取端也可能把真实存在的代码块导出为空内容。若只验证“写入成功”和块数量，表格截断、单元格丢失及反向同步污染都可能被误判为通过。

## 可沉淀经验

### 1. 本地正文与传输载荷必须分层

本地 Markdown 应保持可读、可维护的原始写法；面向在线编辑器的传输层可以生成临时 sidecar，对已知会触发解析歧义的内容做最小编码。不要为了迁就传输端，永久改写本地权威文档。

传输修正要精确到触发模式。例如表格单元格中的空方括号可能被识别为待办语法，应只处理这一模式，不能粗暴转义所有方括号，否则普通链接和其他 Markdown 结构也会受损。

### 2. 安全写法必须通过真实解析器验证

“理论上合法”的 HTML 实体、反斜杠转义或行内代码，不一定在目标编辑器中得到预期显示。应建立最小试验表，分别验证：表格是否保持完整、单元格最终显示是否正确、是否出现多余转义符，再选择传输规则。

当原文中的行内代码与目标解析器冲突时，可以只在 sidecar 中去掉临时代码包装并使用安全转义；本地正文仍保留原语义和样式。

### 3. 表格验收要下钻到单元格

完整验收至少比较每张表的标题、列数、行数和单元格归一化文本，并同时扫描异常待办块、散落管道段落和未替换占位符。只比较表格块总数，无法发现“表仍存在但中间行已散开”的损坏。

### 4. 读取端也可能有损，需按结构选择权威来源

在线文档的 Markdown 导出可能遗漏代码块正文，而结构化表示仍保存完整代码属性。验收和反向同步不能默认把 Markdown 导出当作最高权威；表格、代码块、链接等富结构应从能够保真的结构化来源读取，并记录已知的有损导出行为。

### 5. 同步成功应定义为双向可恢复

写入完成后，不仅要检查线上显示，还要模拟反向读取并确认不会把转义残留、空代码块或拆散的表格覆盖回本地。可靠的完成条件是：本地权威内容、线上结构和反向读取结果在各自允许的表现差异内一致。

### 6. 修复必须进入规则、转换器和回归门禁

一次解析事故的修复应同时进入 Skill 工作流、同步参考、转换脚本和自动测试。回归用例要覆盖触发问题的原始输入，以及链接、行内代码、代码块等容易被连带破坏的结构，避免只修当前文档而让后续同步重复踩坑。

## 适用场景

适用于 Markdown 与钉钉、Confluence、Notion 等富文本系统之间的双向同步，也适用于任何“文本格式作为中间层、结构化编辑器作为终端”的文档流水线。核心原则是：写入成功不是完成，结构完整、表现正确且能够安全回读才是完成。
