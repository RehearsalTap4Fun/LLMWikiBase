# 2026-07-23 Agent 工作流复盘

## 1. 多仓库任务应先确认权威源头

地图配置梳理最初从名称相似的导出/旧仓库开始，后来才确认策划源表位于 K1 配置仓库。虽然部分数值同源，但字段备注、外键粒度和维护责任不同，导致早期结论需要返工。

开局应先回答：

- 当前目录是策划源表、导出产物还是运行时资源？
- 哪个仓库允许修改？
- 另一个仓库是否只是同步结果？
- 客户端和服务端实际消费哪种格式？

对于名称高度相似的仓库，多问一句“哪个是权威源”比后续重做整条关系链便宜得多。

## 2. 外键粒度可用全量取值集合验证

字段名相似并不能证明逐条外键。例如一个字段可能指向对方的分组列，而另一个字段才精确指向记录 ID。

推荐做法：

1. 提取两个候选字段的全量取值集合；
2. 比较交集、覆盖率、重复度和缺失集合；
3. 抽样核对运行时代码；
4. 将关系标记为精确外键、分组匹配或未确认。

这种方法比只看一两行样例或根据字段名猜测更可靠，也适合自动生成配置拓扑图。

## 3. Agent 报告的产物路径必须回到磁盘核验

会话报告声称拓扑图位于一个文件名，但实际磁盘产物是 `C:\Project\K1gdconfig\map_config_topology.html`。文件确实存在，名称却不一致。

因此记录交付物前至少验证：

- 文件实际存在；
- 文件大小和修改时间符合本轮任务；
- 关键内容可搜索；
- 报告路径与真实路径一致；
- 若不一致，以磁盘事实为准并修正摘要。

“Agent 说已生成”不是产物证据。

## 4. 脏工作区拉取远端时要形成可恢复闭环

知识库拉取前存在本地未提交修改。安全流程是：

1. 记录拉取前分支、提交和 `git status`；
2. 暂存本地修改；
3. 执行只允许快进的拉取；
4. 无论拉取成功还是认证失败，都恢复暂存；
5. 对比拉取前后的本地修改清单，确认没有丢失；
6. 报告远端新增/删除文件，不擅自恢复远端有意删除的内容。

第一次拉取因 SSH 认证失败后，本地修改被完整恢复；认证修复后再次执行同一流程，远端快进和本地修改恢复均无冲突。

## 5. SSH 排查要区分“Agent 未运行”和“服务端拒绝公钥”

本轮 ssh-agent 未运行，但 SSH 客户端仍直接读取默认私钥并向 GitHub 提交对应公钥。详细连接日志显示服务端明确拒绝了该公钥，所以根因不是 agent，而是本机当前公钥与 GitHub 登记内容不一致。

推荐排查顺序：

1. 确认私钥和公钥文件存在，并检查最近修改时间；
2. 查看 SSH 实际尝试了哪把钥匙；
3. 对比本地公钥指纹与远端账户登记；
4. 若钥匙近期轮换，确认新公钥是否同步到远端；
5. 用 `ssh -T` 验证身份成功后再执行 Git 操作。

不要因为 ssh-agent 报错就停在第一层判断；关键证据是“实际提交了哪把公钥，以及服务器如何回应”。

## 6. 自动化总结只收录已完成任务

本轮会话中同时存在进行中的设计讨论、已完成配置写入、代码级修复和缺少运行环境的场景验证。总结时必须区分：

- 已完成且有文件/提交/测试证据；
- 代码级验证完成，但真实运行尚未执行；
- 只有需求讨论，没有最终交付；
- Agent 报告与磁盘事实不一致，需要修正。

日报只写第一类和明确标注验证边界的第二类；未完成任务不应为了让日报显得丰富而写成完成事项。

## 可复用清单

1. 多仓库开局先确认权威源和消费格式。
2. 外键关系用全量取值集合与代码双重验证。
3. Agent 产物回到磁盘核对路径、时间和内容。
4. 脏工作区拉取前后都记录状态，并验证暂存恢复。
5. SSH 诊断读取详细连接日志，不只看 ssh-agent 状态。
6. 自动化总结按完成状态和证据等级筛选内容。
