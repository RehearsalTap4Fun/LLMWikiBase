# K1 快速静态预检工作流经验（2026-08-04）

- 回顾范围：2026-08-03 21:30 至 2026-08-04 21:31（Asia/Shanghai）
- 来源：K1 快速静态预检工作流实现与两次真实功能实跑
- 类型：AI/LLM 工程经验原始总结

## 1. 快速预检必须与深度验收使用不同契约

快速预检的目标是尽早发现“当前不适合提测”的确定性问题，而不是在有限时间内伪装成完整验收。本次流程为快速模式设置独立时间预算、精简需求树、有限的一跳证据范围和最多二十条静态用例；原有深度流程继续保留完整证据矩阵和运行验收要求。

两种模式可以共用底层读取与发布工具，但不能共用完成度口径。快速模式未覆盖的需求必须标记为证据不完整或无法确认，不能因为没有发现问题就写成通过。

## 2. 读取 Git 对象可以解除“工作区必须切分支”的约束

预检通过 Git 引用和对象读取目标分支、远端跟踪分支或指定提交，不要求三端工作区切换到目标分支，也不会覆盖用户的未提交改动。执行前后分别计算只读状态摘要，最终只有摘要一致时才能交付报告。

这种方式仍有明确边界：流程禁止在正式仓库中执行 fetch，因此远端跟踪分支只代表本地最后一次同步的状态。需要最新远端证据时，应由用户预先更新引用，或在独立临时仓库中获取；不能为了“自动最新”破坏正式仓库的零写入承诺。

## 3. 需求、用例和证据应形成同源但不同权重的关系

开发文档负责定义需求，自动生成的精简用例负责投影主流程、边界和异常场景，代码与正式配置负责证明实现。用例可以帮助发现遗漏，但不能成为新的需求权威，也不能替代实现证据。

配置核验继续以目标提交中的正式工作簿为准，结构说明文档只用于定位。真实实跑表明，仅比较代码差异会漏掉开关映射、正式邮件配置、权重口径和业务目标是否可完成等跨端问题。

## 4. HTML 摘要、证据报告和测试用例要从同一结果发布

本次工作流从一份经过严格校验的结果生成三类交付物：首屏可读的 HTML 摘要、可审计的 Markdown 证据报告和可继续执行的 Markdown 测试用例。总体结论、问题引用和需求状态由同一结果重算，避免三个文件各自解释导致矛盾。

发布过程使用唯一临时目录和原子发布，并对动态文本转义、引用闭环、固定枚举、路径净化和远程资源进行失败关闭校验。HTML 只改善阅读顺序，不拥有重新解释证据的权力。

## 5. 缓存键必须绑定权威输入，且不能缓存敏感内容

快速模式引入短期缓存，只保存归一需求索引、差异索引和必要的配置查询结果。缓存键绑定文档版本、目标引用和配置对象；任一权威输入变化都必须失效。损坏、过期或越界条目只能返回未命中，不能覆盖报告或删除其他文件。

缓存中不保存凭据、完整开发文档正文或用户工作区内容。这样既能减少重复读取，又不会把“快”建立在证据陈旧或敏感信息落盘之上。

## 6. 时间预算必须进入最终结论，而不是只写在说明里

一次真实预检在预算内完成，另一次因多表格需求和跨端契约核对超出目标时间。流程如实记录超时，没有删减问题或伪造性能指标。这说明后续需要把时间预算做成可中止的阶段门，而不是仅在结束后统计耗时。

当前只有少量真实功能样本，因此可以证明工作流能发现确定性阻断并保持仓库只读，但不能声称已经达到跨功能准确率目标。样本数量、已知限制和运行验收缺口都应继续保留在报告中。
