# 第三方智能体角色库的本地化改造经验（2026-08-11）

- 回顾范围：2026-08-10 21:31 至 2026-08-11 21:30（Asia/Shanghai）
- 来源：通用智能体角色库评估与 K1 本地角色改造设计
- 类型：AI/LLM 使用经验原始总结

## 1. 大型角色库更适合作为素材池，而不是整包安装

角色数量、提示词长度和仓库热度只能说明素材丰富，不能证明这些角色适合当前项目。评估第三方角色库时，应分别检查角色方法是否扎实、是否有实际效果证据、导出格式是否真正利用目标平台能力，以及角色的硬规则会不会覆盖本地项目约定。

对于已经有项目规则、专用 Skills 和多仓库边界的工作环境，更稳妥的做法是挑选少量高价值方法，重写为窄职责组件。通用角色可以提供检查框架，但项目事实、工具路由和权限边界必须来自当前工作区，不能从外部角色提示词继承。

## 2. 本地适配先固定作用域和权限边界

个人使用的角色应安装在用户目录，不向协作仓库写入个人配置，也不在角色中硬编码某一台机器的项目路径。运行时先识别当前工作区，读取适用的 `AGENTS.md`，再根据实际引用决定是否跨仓库检查。

默认只读是合适的基础契约：

- 项目认知角色只解释结构、入口和真实调用链；
- 历史审计角色只报告漂移证据、影响和置信度；
- 经济评估角色默认只读，正式 K1 配置修改必须转交 `config-table-editor`，不得回退到不适用的配置体系；
- 缺少真实 BI 数据时，只能给出模型判断，并明确尚未实证。

这样可以让角色的分析能力与修改权限分离，避免通用角色越过项目已有的专业工具和审批边界。

## 3. 用真实基线决定是否值得创建新角色

改造前先用隔离夹具运行现有通用能力，形成 RED 基线，再运行新角色做对照。如果现有能力已经稳定满足验收契约，就不应为了完成计划而制造失败；可以增加更复杂、相互独立的基线场景，只有同类缺口重复出现时才创建新组件，否则停止该组件。

这种“允许停止”的 Gate 很重要。它把交付目标从“必须产出若干角色”改成“只新增能带来可证明增益的角色”，减少重复能力和后续维护成本。

## 4. 新鲜上下文需要可审计证据

角色评测若要求新鲜上下文、限定读取范围和唯一写入位置，应保存实际派发提示、范围约束、完成结果和原始输出摘要。评审者只能确认记录中可见的事实，不能把工具内部状态或实施者自述当作独立证据。

冻结夹具、评分规则、控制输出和校验摘要，并对这些材料做完整性校验，可以让后续复审判断同一个评测对象。修复评测包时还应验证清单、文件内容和校验值一致，避免“报告说已补证据，但复审包没有包含证据”的断链。

## 5. 验收同时覆盖行为、格式和安装安全

角色或 Skill 的完成条件至少包括：

- 对照场景中的行为缺口得到改善，且没有新增误报；
- 输出包含已检查范围、未检查范围、证据和不确定项；
- 配置文件通过标准解析与官方校验；
- 静态检查确认没有固定项目路径、错误工具路由或写协作仓库指令；
- 真实项目只做受限的只读冒烟验证；
- 只有全部验证通过后，才安装到个人目录。

可复用原则：第三方角色库的价值主要在方法提炼，不在角色数量。先证明本地缺口，再创建窄角色；先验证角色边界，再进行个人安装。
