# 自动化日报补充 Git 提交设计

## 目标

在现有“回顾过去 24 小时会话并生成精炼工作日报”的基础上，增加三端仓库当天 Git 提交采集。仅汇总用户本人直接提交的有效工作，将其转换为业务语言后补充到日报，并与会话来源事项去重。

## 仓库与身份

- 客户端：`C:\Project\K1Client\k1_client`
- 服务端：`C:\Project\K1Game\game`
- 配置端：`C:\Project\K1Dataconfig\dataconfig`
- 作者匹配：提交作者邮箱必须精确等于 `jiangzhenyu@nibirutech.com`

不得仅依赖仓库当前分支。查询范围覆盖仓库全部本地引用，以免遗漏当天已切换分支或已合并到其他本地分支的本人提交。

## 时间与提交筛选

- 时区使用 `Asia/Shanghai`。
- 时间范围为自动化运行当天 `00:00:00` 至实际运行时刻。
- 排除 Merge 提交。
- 先按完整提交哈希去重；哈希只用于内部识别，不出现在日报中。
- 不执行 `git fetch`、`pull` 或其他网络与写操作，只读取本地已有提交。

每条候选提交读取提交标题、正文和改动文件概况。文件内容默认不读取；只有标题和正文不足以判断业务主题时，才可只读查看必要的差异上下文。

## 业务化摘要

Git 提交不得直接复制到日报。摘要应沿用现有标准：只写一条简洁的“具体业务事项 + 结果”，不包含提交哈希、分支名、文件名、字段名、配置 ID、代码术语或实现路径。

如果提交标题和必要差异仍不足以确定业务事项，则舍弃该提交，不猜测结果。修复、调整、配置等提交只有在结果能够被证据支持时才可写入日报。

## 去重与合并

按以下顺序处理：

1. 同一仓库内按完整提交哈希去重。
2. 根据需求编号、业务主题和结果，将同一功能的连续提交合并为一条事项。
3. 跨客户端、服务端和配置端合并同一业务功能，避免按仓库拆成多条。
4. 与会话回顾生成的事项做语义比对；若业务主题与结果相同，保留信息更完整的一条，或合并为一条更完整的业务表述。
5. Git 中存在、会话回顾未覆盖的明确工作事项，作为新条目补入日报。

去重只作用于日报内容，不改变经验总结文件对来源证据的记录方式。

## 输出与发送

最终日报仍只包含“今日完成工作”模块，并沿用现有精炼风格和机器人发送规则。Git 事项与会话事项合并完成后，先生成本地预览，再通过已验证的 Webhook 机器人最多发送一次。

如果当天没有会话工作事项，但存在明确的本人 Git 提交，仍应生成并发送日报。如果两类来源都没有已完成工作，则不生成消息、不发送机器人。

## 异常处理

- 单个仓库不存在、不是 Git 仓库或查询失败时，记录该来源失败并继续处理其他仓库和会话来源。
- Git 查询失败不得阻止已有会话事项生成日报。
- 某个来源失败时，不得把“未查到提交”表述为“当天没有提交”。
- 机器人发送结果不明确时不得盲目重试，继续遵守现有防重复规则。

## 验证场景

以 2026-07-28 当天本地状态作为样例：

- 客户端本人提交“调整委派按钮显示效果”应进入候选集，并被转换为业务化完成事项。
- 配置端其他作者提交的 Google 成就配置不得进入本人候选集。
- 任意 Merge 提交不得进入候选集。
- 若会话回顾已包含委派按钮调整，最终日报只能出现一条相关事项。
- 最终消息不得出现提交哈希、仓库路径、作者邮箱或文件名。
